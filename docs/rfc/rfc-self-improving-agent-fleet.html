The Agent Notebook

Specialized sub-agents that get better at one job — each keeping a tiny notebook of one-line lessons it votes on, capped so hard it can never rot, kept honest by hooks.

design rule: MALIN + KISS — smart, not complex to look clever
cap 200 lines × 120 chars each line has a vote score hooks inject + force retrospective monitored by one log line + nb stats

The whole thing, in four lines

  • ASpecialized roles. The main agent delegates each unit of work to a focused sub-agent role (Cartographer, Reproducer, Patcher, Verifier…) that gets good at one thing.
  • BA bounded notebook. Each role keeps a plain-text notebook: ≤ 200 lines, one lesson per line, ≤ 120 characters, each line with a vote score. Full → the lowest-scored line falls off. The hard cap is the safety.
  • CThe agent curates. End of task it votes +1 on what helped, −1 on what misled it, and when full it consolidates or deletes a weak line itself.
  • DHooks + a fast CLI guarantee it. A start hook injects the notebook; a stop hook blocks until the retrospective is done; the local nb command (plain text, no network) is faster and more reliable than kb, and monitors itself.

01Why

Two gaps today — and the usual fix for the second is what makes systems complex.

Agents don't specialize. One agent does nearly everything; no focused role gets sharp at a single kind of job.

Agents don't learn. They finish and keep nothing. Kookr's existing lesson store is the opposite extreme — forced to grow (1,319 notes and counting) with no bound, so it rots: noise, stale and contradictory entries, context that drowns the signal.

The trap we refuse

"Add memory" normally means "add an unbounded store + a retrieval system + a pruning system." That spiral sank an earlier, over-built version of this RFC. We make the bound structural, let the agent curate within it, and let hooks guarantee the ritual — then none of that machinery is needed.

02The notebook

A new memory type: tiny, plain text, with a vote score per line. Its limits — and the agent's votes — do all the work.

PropertyWhat it buys you
Whole notebook fits in context
200 × ~120 ≈ 24 KB		The role just reads the entire notebook at task start. No retrieval, no ranking, no injection scoring.

03Hooks make it trustworthy

A rule in a prompt is a suggestion; a hook is a guarantee the harness enforces. Kookr already works this way — we reuse it so the ritual can't be skipped.

One fast, reliable command — nb (kb-shaped, but plain text)

nb show   <role>                      # print the notebook (the start hook calls this)
nb add    <role> "<lesson>"           # dedup-skip, score +1, write, trim (lowest-score out)
nb vote   <role> <id|query> +1|-1     # adjust a score  (the stop hook calls this)
nb merge  <role> <idA> <idB> "<merged>" # consolidate two entries into one
nb rm     <role> <id|query>           # delete an entry the agent judges useless
nb stats  [<role>] [--since 7d]       # usage analytics + anomaly flags
nb --help                             # the documented entry point

Because a notebook is local plain text — no FAISS, no embeddings, no Ollama, no network — nb is faster and more reliable than kb and has no spool-degradation failure mode. Every operation is a millisecond, deterministic, offline file edit under a lock.

04Monitored — without a monitoring system

Same dumb-but-sufficient trick as the notebook: every nb call appends one line to a capped usage log; nb stats reads it. No metrics server, no dashboard to stand up.

# ~/.kookr/notebooks/.nb-usage.log  — one line per call, oldest-dropped ring
2026-10-22T21:40:11Z  patcher   add    ok   7ms
2026-10-22T21:40:12Z  patcher   vote   ok   3ms
2026-10-22T21:41:02Z  verifier  show   ok   2ms

Then nb stats turns that into call counts, error rate, p50/p95 latency, last-used — and flags the three anomalies you'd actually want to catch:

called in a loop

same role + command many times in a tight window → the agent is stuck or looping.

went silent

a command that was used drops to zero → it probably broke or stopped behaving as expected.

high error rate

a command erroring often → broken, or not doing what the agent expects.

How to reach the tool and its analytics lives in one short page, docs/reference/agent-notebook.md — the single source for operating and improving it.

05The roles

A small starter set (capability-shaped, not human job titles) that grows as needs appear. The main agent stays the orchestrator — pick a role, hand a short brief, get a result back.

06What we build — and what we don't

The whole build is a small CLI, two hooks, a few role files, and one doc page. The rest is a deliberate list of things we are not doing.

Build (small)

  • +The nb CLI + notebook format (+ the one-line usage log & nb stats) — ~1 small module, plain text + file lock.
  • +Two hooks: a SessionStart injector and a Stop retrospective-gate (block-then-instruct).
  • +A few plugin/agents/<role>.md role definitions that vote/curate in their retrospective.
  • +One doc page: docs/reference/agent-notebook.md (how to use the tool + read its analytics).

Don't build (the old complexity)

  • −No embeddings / FAISS / semantic retrieval — read the notebook whole.
  • −No decay scoring or bi-temporal invalidation — just the agent's vote.
  • −No kb demote actuator, janitor playbook, or scheduled purge — eviction is inline, curation is the agent's.
  • −No metrics server or dashboard — one log line per call + nb stats.

07Open questions

  1. Vote → eviction: pure lowest-score-then-oldest is the default. Add a floor (never auto-evict a line scored ≥ k) only if useful lines get lost.
  2. Scope: one notebook per role (default), or per role × per repo for repo-specific roles (e.g. Cartographer). Add a <role>@<repo> suffix only where clearly needed.
  3. The numbers: 200 lines / 120 chars to start — tune only if real notebooks show useful lessons truncated or aged out too fast.
