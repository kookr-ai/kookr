## Problem

Kookr has meaningful test coverage, but the health of that coverage is hard to see unless a developer already knows which commands and CI jobs to inspect.

Current state:

| Surface | Observation |
|---|---|
| README badges | Shows CI status, stars, last commit, TypeScript strict, Node version, license. It does not show testing breadth or coverage. |
| `package.json` | Exposes `test`, `test:coverage`, `check:e2e`, `test:hooks`, and Playwright commands. |
| `vitest.config.ts` | Coverage is configured with V8 and emits `text`, `html`, and `lcov` into `coverage/`. |
| `.github/workflows/ci.yml` | Runs server typecheck, E2E typecheck, skill validation, unit tests, hook tests, build, and Playwright E2E. It uploads the Playwright report only on failure. |
| `.github/workflows/e2e.yml` | Manual `/run-e2e` workflow uploads Playwright report on every run and comments the result on the PR. |
| PR template | Asks authors to check unit tests, E2E, canary, appropriate coverage, and docs drift. |

The gap is not "Kookr has no tests." The gap is that contributors, reviewers, and supervised agents cannot quickly answer:

- Which test suites protect the project?
- Did this PR preserve or improve coverage?
- Where is the CI report for a failed test run?
- Is a README coverage badge trustworthy or just stale decoration?

This matters because Kookr is an agent supervisor. Its bugs often live in orchestration, hooks, process lifecycle, terminal sessions, WebSocket state, and browser UI. A single green CI badge does not explain which layer was exercised, and a static README percentage would become misleading the first time it drifted from CI.

## Goals

- Make test health visible from the README without turning the README into a dashboard.
- Give every PR a machine-generated testing summary that reviewers can inspect without downloading logs.
- Preserve detailed artifacts for failures and coverage investigations.
- Keep the first implementation local to GitHub Actions and existing tools. No new SaaS account is required for V1.
- Make stale or unverifiable coverage numbers impossible to publish accidentally.

## Non-goals

- No Codecov/Coveralls adoption in V1. It may be useful later, but it adds an external dependency before Kookr has proven what signal it wants.
- No failing coverage threshold in the first PR. A threshold before a ratcheted baseline will incentivize broad, shallow tests or gaming exclusions.
- No README badge with a manually edited coverage percentage.
- No expansion of product test scope in this RFC. This RFC improves surfacing; it does not decide which missing tests to write.
- No always-uploaded heavy Playwright HTML report from the default CI unless a run fails. The manual `/run-e2e` workflow already uploads it on every requested run.

## Requirements

- The README must expose a concise "test health" entry point that links to CI and a repo-local explanation of what runs.
- The default CI must produce a PR-visible summary of unit coverage totals: statements, branches, functions, and lines.
- The default CI must upload machine-readable coverage artifacts on every PR run.
- Failed browser runs must keep uploading Playwright HTML reports, as today.
- The source of any public coverage number must be generated by CI from the `main` branch or from the current PR run; it must not be hand-edited.
- The PR template must point authors to the generated summary instead of asking them to manually infer coverage from logs.
- The design must work on forks and Dependabot PRs without privileged secrets.

## Recommendation

Ship CI-generated reports first; defer a README coverage percentage badge.

The README should gain a small testing link via the "Where To Go Next" table — **no new badge**. A content-free "Test Health" badge linking to a markdown file says nothing the existing CI badge does not already imply, and would be the cargo-cult version of the hand-edited percentage this RFC rejects elsewhere. `docs/testing.md` is the discoverable entry point; the table row is the link.

The coverage percentage becomes badge-worthy only after one of these sources exists:

1. A CI-generated badge artifact published from `main` to a stable URL, or
2. A coverage service with a public badge backed by the latest `main` run.

Until then, a README percentage is worse than no percentage: it creates a public trust surface with no enforcement.

## Design

### Change 1 - Add `docs/testing.md`

Create a durable testing overview:

- Suite inventory:
  - `pnpm test` - Vitest unit tests under `src/**/*.test.ts`.
  - `pnpm test:coverage` - Vitest with V8 coverage.
  - `pnpm check:e2e` - TypeScript check for Playwright tests.
  - `pnpm exec playwright test` - browser E2E.
  - `pnpm test:hooks` - shell regression tests for project hooks.
  - `CANARY=1 pnpm exec playwright test e2e/canary.spec.ts` - real-agent canary, local/manual due API cost.
- CI mapping:
  - Which workflow runs which command.
  - Which artifacts are uploaded and when.
  - Which checks are required before merge.
- Interpretation rules:
  - Coverage is a trend and gap-finding signal, not a target by itself.
  - The published number covers all of `src` (frontend included post-PR #1169; see Change 6 supersession note).
  - Branch coverage is usually the most useful early warning for orchestration code.
  - Browser report artifacts are for failed or manually requested E2E runs.
- **Navigation bridge** — explicit step-by-step instruction so a reader who lands on the README badge can find the live numbers without guessing: "Open the PR's Checks tab → click the `test` job → click `Summary` in the left sidebar → the coverage table is at the bottom." Without this, the README → docs/testing.md → live-numbers path has an invisible third hop that defeats the discoverability goal.
- Local commands for reproducing CI, including the script preview: `pnpm test:coverage && node --import tsx scripts/coverage-summary.ts coverage/coverage-summary.json`. Contributors should be able to see locally what the PR run will print.
- **Troubleshooting / operator runbook** (short):
  - **Coverage artifact missing on a PR.** Check the `Run tests with coverage` step; if it exited non-zero, that is the upstream cause. `--coverage.reportOnFailure` is set, so the directory should still exist on test failures.
  - **Step summary is blank but the job is green.** Run the script locally against the artifact's `coverage-summary.json`. If it prints output locally, the issue is in the workflow's redirect to `$GITHUB_STEP_SUMMARY`.
  - **Coverage numbers look implausibly low or high.** Inspect `vitest.config.ts` include/exclude — a new untested directory under `src/` is the most common source of aggregate dilution (frontend is included; see Change 6 supersession note).
  - **`::error::` annotation in the Checks UI.** Read the annotation text; it distinguishes "JSON malformed" from "script crashed" (see Change 3 contract).

This gives agents and humans one stable place to answer "what testing means in this repo" and a short runbook for the next operator who hits a weird CI run.

### Change 2 - Generate coverage summary in CI

Extend the `test` job in `.github/workflows/ci.yml`.

Replace the current unit-test step:

```yaml
- name: Run tests
  run: pnpm test
```

with a coverage-producing unit-test step:

```yaml
- name: Run tests with coverage
  run: pnpm exec vitest run --coverage --coverage.reportOnFailure --coverage.reporter=text-summary --coverage.reporter=json-summary --coverage.reporter=lcov
```

`--coverage.reportOnFailure` is load-bearing. Without it, Vitest exits before finalizing the `coverage/` directory when any test fails, so the artifact upload runs against nothing and reviewers cannot inspect coverage on the runs where it would be most useful. Verified with vitest 4.1.5 / `@vitest/coverage-v8` 4.1.5 / `istanbul-reports` 3.2.0 (delivery-pragmatist, 2026-05-13).

Then upload lightweight artifacts:

```yaml
- name: Upload coverage artifacts
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: coverage
    path: |
      coverage/coverage-summary.json
      coverage/lcov.info
    retention-days: 14
```

Do not upload the full HTML coverage report by default. It is useful locally, but it is large enough to become CI noise. If reviewers need HTML later, add it to a manual workflow or upload it only on failure.

### Change 3 - Write a GitHub Actions step summary

Add `scripts/coverage-summary.ts`:

```yaml
- name: Summarize coverage
  if: always()
  run: node --import tsx scripts/coverage-summary.ts coverage/coverage-summary.json >> "$GITHUB_STEP_SUMMARY"
```

The script emits a compact Markdown table:

| Metric | Covered | Total | Percent |
|---|---:|---:|---:|
| Lines | n | n | n% |
| Statements | n | n | n% |
| Branches | n | n | n% |
| Functions | n | n | n% |

It also prints:

- A one-line header noting this is current-run coverage with no baseline comparison yet — that ratchet ships in PR 2.
- Top 10 files by uncovered lines, **only when total line coverage is below 80%** (suppressed otherwise to avoid noise on healthy PRs).
- Top 10 files by uncovered branches, **only when total branch coverage is below 70%** (same rationale).
- A named-layer breakdown table for the five risk areas the Problem section identifies (orchestration, hooks, process lifecycle, terminal sessions, WebSocket state), mapped by path patterns inside the script. This makes the surface honest about the layers Kookr's bugs actually live in instead of producing a flat top-10 dominated by file size.

This is the primary reviewer surface. It avoids third-party actions and does not require GitHub token permissions beyond the default step summary file.

The script's exit-code contract must distinguish three failure modes — silent exit-0 on every path would hide its own bugs:

| Condition | Exit code | GitHub Actions annotation |
|---|---:|---|
| `coverage-summary.json` does not exist | 0 | `::notice::` "Coverage data unavailable — tests likely failed before coverage finalized; see the test step logs." |
| File exists but is empty or unparseable | 1 | `::error::` "Coverage JSON malformed at <path>; rerun job or inspect uploaded artifact." |
| Unexpected runtime error in the script itself | 1 | `::error::` "coverage-summary.ts crashed: <message>." |
| Normal run | 0 | (none — Markdown table only) |

The `::error::` annotations surface in the PR Checks UI without requiring reviewers to navigate the raw job log. The test step itself remains the source of truth for test pass/fail; the script never converts a test failure into a green check.

### Change 4 - Add a README testing entry point

Add one row to the "Where To Go Next" table — no new badge.

| I want to... | Read |
| --- | --- |
| Understand test suites and coverage reports | [Testing](docs/testing.md) |

This makes test surfacing discoverable without overloading the badge row or adding a decorative element that says nothing the existing CI badge does not already imply. A second non-numeric badge would be cargo-cult: it would mirror the structure of "real" coverage badges without their information content.

### Change 5 - Update the PR template

Replace the vague "covered by appropriate tests" checklist item with a more concrete one:

```markdown
- [ ] Reviewed the CI test summary and any uploaded coverage artifacts for this PR.
- [ ] Added or updated tests for the changed behavior, or explained why this change is docs/config-only.
```

Keep the existing explicit unit, E2E, canary, and docs-drift checklist items. They are useful because CI cannot run the API-cost canary on every PR.

### Change 6 - Lock the frontend-exclusion decision before shipping PR 1

> **Historical (PR 1 ship).** Superseded when frontend entered coverage (#1169);
> operator copy corrected in #1426. Live include list: all of `src/**/*.{ts,tsx}`
> minus tests and `src/server/start.ts`.

`vitest.config.ts` **originally** excluded `src/frontend/**`, `src/**/*.test.ts`, and `src/server/start.ts` from V8 coverage. The number the step summary printed in PR 1 was therefore a backend/server/core number, not a whole-repo number. This RFC committed to keeping that exclusion for PR 1 and ratchet phases.

Rationale:

- V8 coverage cannot meaningfully instrument React components without a frontend test harness; including them would emit near-zero coverage for the entire `src/frontend/**` tree and drag the headline number down for no diagnostic benefit.
- Including the frontend would couple two unresolved questions — "do we have backend coverage signal?" and "how do we cover the frontend?" — into one decision and stall both.
- The exclusion is recorded in code (`vitest.config.ts`) and will be called out in `docs/testing.md` so reviewers do not mistake the number for whole-repo coverage.

A frontend coverage strategy was explicitly out of scope for this RFC at write time. PR 1 published a backend coverage number with an explicit "(server/core; frontend excluded)" subtitle in the step summary. Frontend later entered the aggregate (#1169); the live subtitle and `docs/testing.md` now describe whole-`src` coverage (#1426).

### Change 7 - Add a main-branch badge only after there is a generated source

Do not ship this in PR 1.

If the team still wants a README percentage badge after living with CI summaries, pick one:

**Option A - External coverage service.** Upload `lcov.info` from `main` and PRs to Codecov/Coveralls, use the provider badge. Lowest custom code, external dependency.

**Option B - GitHub Pages badge.** On `main`, generate a small JSON/SVG badge from `coverage-summary.json` and publish it to GitHub Pages. No SaaS dependency, but it adds Pages setup and a new publishing workflow.

**Option C - Generated markdown file.** Commit no badge, but publish `docs/reports/latest-coverage.md` from CI. Rejected for now because CI committing to `main` adds more workflow risk than the signal is worth.

Recommendation if this becomes important: Option A if external coverage history is acceptable; Option B if Kookr wants to stay GitHub-only.

## Implementation phases

### PR 1 - Local GitHub-native surfacing

Add `docs/testing.md`, README entry point, PR-template wording, CI coverage artifacts, and the step-summary script.

Acceptance criteria:

- A PR run shows a "Coverage summary" table in the GitHub Actions job summary, including the named-layer breakdown and the coverage-scope subtitle (originally "(server/core; frontend excluded)"; later whole-`src` after frontend inclusion).
- The `coverage` artifact contains `coverage-summary.json` and `lcov.info` on both passing and failing test runs (because `--coverage.reportOnFailure` is set).
- README links readers to `docs/testing.md` via the "Where To Go Next" table row (no new badge).
- `docs/testing.md` includes the explicit "Checks tab → test job → Summary tab" navigation bridge to the live numbers.
- The coverage-summary script emits distinct exit codes / annotations for missing JSON vs malformed JSON vs script crash (Change 3 contract).
- No external service or secret is required.

A draft PR is opened first to verify the workflow actually runs end-to-end on this repo before merge — the validation notes record that local coverage could not be exercised in the RFC worktree due to missing dependencies, so first-CI-run is the empirical check.

### PR 2 - Baseline and ratchet

**Trigger (concrete, observable):** PR 2 work begins once at least **5 merged PRs targeting `main`** have each produced a `coverage-summary.json` artifact with no missing-data warning. The owner is the next person reviewing a PR that hits this threshold; they are responsible either for opening PR 2 or for recording a written reason to defer it in the RFC's status line.

This trigger is deliberately shippable and falsifiable. "Several PRs" with no count or owner is the failure mode this version corrects — without a concrete trigger, the soft ratchet is the mechanism that makes PR 1's number actionable, and indefinite deferral means PR 1 produces a vanity number contributors learn to ignore.

**Initial rules to evaluate against real data:**

- Warn when total line coverage drops by more than 1 percentage point versus the `main` baseline.
- Warn when branch coverage drops by more than 2 percentage points.
- Fail only when coverage data is missing unexpectedly (the `::error::` path from Change 3 already covers script crashes and malformed JSON).

The baseline is the per-PR `coverage-summary.json` from the latest successful `main` run; PR 2 adds a workflow step that downloads it via `actions/download-artifact` or stores it in the repo as `.coverage-baseline.json`. The choice between the two storage approaches is the only real design question PR 2 has to answer.

Do not fail PRs for ordinary coverage movement until the team has reviewed real trend data. A noisy gate teaches contributors to work around the gate.

### PR 3 - Public percentage badge, if still wanted

Adopt Codecov/Coveralls or publish a GitHub Pages badge from `main`.

**Decision gate (timeline-based, not behavior-based):** PR 3 ships within **30 days of PR 2 merging**, or the maintainer records a written reason in this RFC's status line to skip it. "Actively used during review" was the previous gate; it is not measurable (GitHub does not expose step-summary view counts) and would default to "cannot confirm, defer again" indefinitely. A timeline gate with an explicit skip-with-reason path forces the decision instead of letting it drift.

Acceptable skip reasons include: PR 2's data revealed coverage is misleading (e.g., a major refactor invalidated the baseline), the team explicitly decided a public number adds no value, or external scrutiny of the project does not warrant the publishing workflow.

Note on the staleness anti-pattern: any badge sourced from `main` shares one failure mode with the hand-edited number this RFC rejected — if the publishing workflow breaks silently, the badge freezes at the last successful value with no visible age signal. PR 3 must either (a) include a "last updated" subtitle on the badge image itself (the shields.io endpoint supports this) or (b) emit a CI annotation when the badge job has not run successfully against `main` in the last 7 days. Without one of those, Option B is a slower version of the hand-edited badge.

## Alternatives considered

### A. Add a README coverage badge immediately

Rejected for V1.

Coverage badges are useful only when they are backed by a current, generated source. A manually edited badge or static shields.io number is actively misleading. Kookr should not publish a number that reviewers cannot trace back to a specific CI run.

### B. Use Codecov/Coveralls immediately

Deferred.

This is the fastest way to get badges, PR comments, and trends. The tradeoff is external dependency and new workflow surface area. Kookr can avoid that until it has confirmed that coverage summaries influence review decisions.

### C. Upload full HTML coverage on every PR

Rejected for default CI.

HTML is useful for local investigation and occasional debugging, but most reviewers need the top-level table and worst offenders. Uploading full HTML on every PR creates artifact noise. Keep `html` local via `pnpm test:coverage`; upload JSON/LCOV by default.

### D. Add hard coverage thresholds now

Rejected for V1.

Thresholds are useful after a baseline is understood. Adding them before the first surfaced baseline risks optimizing for the number rather than the missing risk. The first surfacing PR should gather signal.

### E. Rely only on the existing CI badge

Rejected.

The CI badge answers "did the default workflow pass on main." It does not answer what ran, what coverage changed, where reports are, or whether a failure was unit, hook, build, or browser related.

### F. Use a marketplace action (e.g., `davelosert/vitest-coverage-report-action`)

Considered, deferred.

Off-the-shelf actions exist that consume Vitest's coverage output and post sticky PR comments with line/branch coverage and diff-vs-base — without a SaaS account, using only `GITHUB_TOKEN`. They would shrink Change 3 to roughly a 10-line `uses:` block instead of a custom TypeScript script.

The tradeoffs against the custom-script choice in this RFC:

- **Output shape.** The custom script can emit the named-layer breakdown (orchestration, hooks, lifecycle, sessions, WebSocket) that the Problem section explicitly names as Kookr's bug-prone areas. A marketplace action emits a generic top-N list. The layer-aware view is the design's clearest connection to the RFC's stated motivation.
- **PR comment vs step summary.** The marketplace action posts a sticky PR comment, which is more discoverable than the step summary. This is a real ergonomic win and the strongest argument in favor of the action. The cost is `pull-requests: write` token permissions, which require care on fork PRs and Dependabot PRs (the action's docs spell out the `pull_request_target` patterns).
- **Maintenance.** The custom script is ~100 lines and depends only on Vitest's JSON output. The marketplace action is third-party code with its own release cadence and security surface.

**Decision:** ship the custom script in PR 1 because the layer-aware breakdown is the part that earns the RFC's motivation. Add the marketplace action to the PR 2 evaluation: if reviewers report they would rather have a sticky PR comment than a step-summary table — and the named-layer view turns out to add little real signal — swap the custom script for the action in PR 2.

This is a falsifiable swap point, not a permanent rejection.

## Edge cases

- **Tests fail before coverage finalizes.** The summary script must print "coverage summary unavailable" and link to logs rather than failing with a confusing parser error.
- **Forked PRs.** Artifact upload and step summaries must work without repository secrets.
- **Dependabot PRs.** The workflow must not require write permissions or privileged PR comments.
- **Large LCOV files.** Retention is 14 days; only JSON and LCOV are uploaded by default.
- **No `node_modules` in a fresh worktree.** Local coverage commands require `pnpm install --frozen-lockfile`; `docs/testing.md` should say so.
- **Coverage includes all of `src` (post-#1169).** Risk-layer patterns intentionally avoid `/hooks/` so React `src/frontend/hooks/**` does not pollute the Hooks layer (`scripts/coverage-summary.ts`, #1426). Live wording: `docs/testing.md` + step-summary subtitle.
- **E2E reports.** Default CI keeps failure-only Playwright report upload; manual `/run-e2e` keeps always-upload behavior.

## Open questions

- Should `pnpm test` remain a fast no-coverage command locally while CI uses coverage, or should `pnpm test` and CI stay identical? (Default in this RFC: keep `pnpm test` fast; CI runs `vitest run --coverage ...`.)
- Should `staging.yml` mirror the new coverage step, or stay as plain `pnpm test`? (Default in this RFC: stay plain — staging PRs are infrequent enough that diverging from `ci.yml` is acceptable for PR 1; revisit in PR 2 if staging churn grows.)
- Is a GitHub Pages badge acceptable if the team wants a no-SaaS public percentage badge? (Resolved enough that PR 3 lists it as Option B; the open part is whether the team wants any public number at all.)

(The earlier "include frontend in coverage?" and "compare against origin/main in PR 1?" questions were resolved for PR 1 as: keep frontend excluded, defer baseline diff to PR 2. Frontend later entered coverage in #1169; see Change 6 supersession note and #1426 for operator-copy repair.)

## Critic feedback incorporated

### Round 1 (v1 → v2, 2026-05-13)

- **Boundary critic, local pass:** Split durable docs, CI artifacts, and README badges into separate responsibilities. The RFC now rejects hand-edited README percentages and makes CI the source of truth.
- **Failure-mode analyst, local pass:** Added fork, Dependabot, missing coverage, and frontend-exclusion edge cases.
- **Design minimalist, local pass:** Removed full HTML coverage upload from default CI and deferred thresholds, external services, and public percentage badges.
- **Socratic challenger, local pass:** Made the badge decision explicit: first prove the PR summary is useful, then add a public number only if it has a generated source.
- **Ambition amplifier vs design minimalist resolution:** Chose the minimalist V1 because the load-bearing question is discoverability and trust, not long-term coverage analytics. The larger analytics path remains available as PR 2/3 after real usage.

### Round 2 (v2 → v3, 2026-05-13)

- **Delivery pragmatist, round 2: novel finding.** Identified the missing `--coverage.reportOnFailure` flag — without it, no coverage artifact is produced on the runs where it would be most useful. Also empirically verified that the CLI flag combination works with vitest 4.1.5 / `@vitest/coverage-v8` 4.1.5 / `istanbul-reports` 3.2.0, closing the validation-notes gap and replacing the need for a separate PR0 scout. Sharpened PR 2's trigger (5+ artifact-producing PRs, named owner) and PR 3's gate (30-day timeline post-PR2 with explicit skip-with-reason).
- **Operability reviewer, round 2: novel finding.** Identified three runtime gaps: step summary discoverability (no navigation path from README), exit-0-on-missing-JSON conflating script bugs with absent data, no GitHub Actions annotations on error paths. RFC now specifies an exit-code contract with `::notice::` / `::error::` annotations and a navigation bridge in `docs/testing.md`. Added the operator runbook section.
- **Ambition amplifier, round 2: novel finding.** Forced the frontend-exclusion decision in-place (Change 6) instead of leaving it as a post-ship Open Question — shipping a number with an undisclosed denominator was a structural flinch the v2 had not yet resolved. Also pushed the named-layer breakdown (orchestration/hooks/lifecycle/sessions/WebSocket) into the script's output so the surface actually earns the Problem section's framing rather than emitting a generic top-10 list. PR 2 / PR 3 vagueness was the second hard part being dodged; concrete triggers above.
- **Socratic challenger, round 2: novel finding.** Removed the decorative "Test Health" badge — a non-numeric shields.io badge linking to a markdown file was the cargo-cult mirror of the hand-edited percentage this RFC rejects elsewhere. Added the marketplace-action alternative (`davelosert/vitest-coverage-report-action`) to the Alternatives section with an explicit falsifiable swap point at PR 2: the custom script ships for layer-aware output, but a swap is on the table if reviewers prefer sticky PR comments and the layer view turns out to add little signal. The "reverse PR 1 and PR 2" alternative was considered and rejected: a baseline ratchet without a baseline-producing first run has no source to compare against, so the current ordering is required.
- **Ambition amplifier vs design minimalist resolution, round 2:** Resolved in favor of ambition this round — the frontend-exclusion decision and the named-layer breakdown were both "comfortable to defer" rather than "load-bearing future work," and locking them now closes loops the design-minimalist V1 left open. The minimalist round-1 boundary still holds for thresholds, public badges, and external services.
- **Empirical validation checkpoint (post round 1, executed in round 2):** The load-bearing empirical claim — that `vitest --coverage` with stacked `--coverage.reporter=...` flags emits both `coverage-summary.json` and `lcov.info` against this repo's installed toolchain — was verified by the delivery-pragmatist agent against the installed vitest 4.1.5 stack. No probe falsified the design; no further design-experimenter pass is needed before round 3.

### Stop criterion

No round 3 is planned unless the user surfaces a new dimension. Round 2 produced four novel findings, all of which have been incorporated; the remaining items (verbosity tuning, marketplace action swap evaluation) are deferred to PR 2 with concrete triggers rather than as new RFC scope.
