# RFC: Task-Completion Chime — Move from Global Stop Hook to Browser

**Status:** Draft (v3 — post round-2 critic incorporation)
**Date:** 2026-05-10
**Author:** Jean Ibarz (with Claude)

---

## Problem

The user has a global Claude Code Stop hook in `~/.claude/settings.json:74` that plays `task-complete.wav`:

```json
"Stop": [{ "matcher": "", "hooks": [{ "type": "command",
  "command": "(play -q $HOME/.claude/sounds/task-complete.wav &) 2>/dev/null; true" }] }]
```

(The literal hook in the user's settings hardcodes their absolute home path; the snippet above is normalized to `$HOME` for documentation portability.)

This produces a "storm" of chimes because:

1. `Stop` fires on **every assistant turn end**, not just task completion. Each turn of any session triggers it.
2. Kookr spawns many parallel Claude Code sessions (ralph loops, scout subagents, one-shot tasks, manual chats). Every spawned session has its own Stop hook firing independently.
3. There is **no env-var discriminator** for the "user-attached/foreground" session — `KOOKR_TASK_ID` is set on every spawned session, including the one the user is currently typing into.

The shell-hook approach is fundamentally mismatched to the user's intent: the chime should fire when *the task the user is currently watching* reaches a noteworthy lifecycle event. That signal lives in the dashboard, not in the agent process.

## Empirical Checkpoint

The relevant frontend infrastructure already exists and was verified by inspection:

- `src/frontend/hooks/useAudibleAlert.ts` already plays a Web-Audio chime for **anomaly findings** (warnings/criticals). It implements: localStorage mute toggle (`kookr-sound-enabled`), DND respect (`isDndEnabled()`), per-tab dedup, post-clear cooldown, and graceful handling of browser autoplay rejection.
- `src/frontend/hooks/useNotifications.ts` shows browser Notifications when `document.hidden` and a new finding appears. Permission-request and click-to-focus flow are already wired.
- `selectedAgentId` exists in `useKookrStore` and represents the agent currently focused in `DetailPanel`. Each agent carries `taskStatus` and `taskId`.
- `task_completed`, `task_terminated`, `task_cancelled` are already emitted by the server (`src/server/agent-lifecycle.ts:244`, `:279`, `:314`) and propagate to the frontend through the existing `taskStatus` field on `AgentState` snapshots and deltas. (Round-1 correction: they propagate as a `taskStatus` field update, not as named events in `client-message-schema.ts`. The previous v1 citation of `client-message-schema.ts:45-46` was wrong — that schema lists telemetry event names sent *from* the frontend, not lifecycle events received *by* it.)
- The audio is generated by `AudioContext` oscillators (no asset bundling). Web Audio's autoplay-policy gracefully degrades — the existing hook ignores rejection — and is unblocked the moment the user interacts with the page.

So the RFC is largely additive: a second trigger source for the same chime infrastructure, with the focus-gate that the existing finding chime does not currently apply.

**Pre-extraction empirical gap (round-1 delivery-pragmatist finding):** `useAudibleAlert.test.ts` exercises only `evaluateChime` and the localStorage helpers. It never stubs `AudioContext` or asserts that the audio path runs. Without coverage, refactoring `playChime` out of `useAudibleAlert.ts` could silently break the finding chime and CI would stay green. The test plan below adds a smoke assertion *before* the extraction lands.

## Requirements

- The audible chime SHALL play when the task currently focused in the dashboard transitions into a terminal status (`completed`, `terminated`, or `cancelled`), where the transition is observed *while the agent is focused*.
- The chime SHALL NOT play for transitions observed before the user focused the agent. In particular: switching focus to an already-terminal agent SHALL NOT chime, even if the user previously had it focused and left.
- The chime SHALL NOT play if no task is focused (`selectedAgentId === null`).
- The chime SHALL respect the existing sound-enabled toggle and DND state — same gates as `useAudibleAlert`.
- The chime SHALL be deduped: a single terminal transition produces at most one chime, even if the same `AgentState` is re-emitted by snapshot/delta merges.
- The chime SHALL NOT play on initial dashboard load when the focused task is *already* terminal at hydration time. Only fresh transitions chime.
- The user SHALL be able to use the existing localStorage mute toggle (`kookr-sound-enabled`) to silence both completion and finding chimes uniformly. (No new preference key.)
- AudioContext rejection (browser autoplay policy) SHALL be detectable: a one-time `console.warn` per tab SHALL fire on the first rejection, so a silent-failure mode is diagnosable from devtools.
- The global Claude Code Stop hook in `~/.claude/settings.json` SHALL be removed by the user after dashboard verification.
- The change SHALL NOT regress the existing finding chime. A pre-existing audio-path smoke test SHALL guard the `playChime` extraction.

## Non-Goals (v1)

- A generalized in-app notifications/toast system.
- Replacing the existing finding chime's behavior or sound. The two triggers share the same two-tone `playChime` in v1; distinct sounds per event are an Open Question (below).
- Multiple-tab coordination. Each tab independently chimes for *its own* focused task.
- Replicating the chime for users who run Claude Code outside Kookr.

## Open Questions for User Decision

Three real UX trade-offs surfaced from round-1 critics that the spec cannot resolve without user intent. The RFC assumes the conservative answer to each, marked with †. The user should confirm or override before implementation.

(Round-2 design-minimalist note: the previous v2 also listed "user-initiated chime" as an Open Question, but the spec already chimes on user-initiated completion — that is current behavior, not an open question. It is now captured as a follow-on enhancement under §Future enhancements rather than a v1 decision blocker.)

1. **Distinct sounds for `terminated` / `cancelled` / `completed`?**
   `completed` is a celebration. `terminated` (sessions died, user did not ack) is a *bad* event. The current two-tone rising chime is identical for both, which the existing `useAudibleAlert.ts` describes as "for urgency." †Default: same chime for all three. Alternative: distinct sounds (rising for completed, falling for cancelled, longer/lower for terminated). Cost: ~30 lines for two more `playChime*` variants.

2. **OS desktop notification when focused task completes and tab is hidden?**
   The existing `useNotifications.ts` already shows OS notifications for findings when `document.hidden`. Symmetric extension to focused-task completions is ~10 lines and would solve the "I walked away from the laptop and want to know it finished" use case that Web Audio cannot reach when the tab is backgrounded by the OS. †Default: out of scope (audio chime only). Alternative: extend `useNotifications.ts` for the focused-completion case in the same RFC.

3. **Long-running background-task completion — silent or chime regardless of focus?**
   Current spec is silent for non-focused tasks. socratic-challenger and ambition-amplifier argued that audio is *most* useful precisely when the user is *not* watching a long task: a 6-hour ralph finishes while the user is in a different task; per spec, no audible signal until the user happens to glance at the completed list. †Default: silent (matches user's stated intent: "only when main agent finished its task"). Alternative: chime for any task whose `runtime > N minutes` (e.g., 10) regardless of focus. Cost: a duration check using `task.createdAt`; risk: re-introduces a smaller "storm" if the user has many parallel long tasks.

## Design

### 1. Module structure

Round-1 critics surfaced a conflict: design-minimalist argued against the v1 three-file split (no real circular import); boundary-critic argued that mute/DND/`playChime` policy belongs in a non-hooks shared module so future chime triggers don't duplicate the gate inline. The synthesis below collapses both into **one new module** plus the new hook:

| Path | Responsibility |
|------|----------------|
| `src/frontend/audio/sound.ts` | **New.** Owns the chime function, the sound-enabled preference, and the gate. Exports: `playChime()` (raw oscillator, used directly only by tests), `maybePlayChime()` (gate-aware: returns early if mute or DND), `isSoundEnabled()`/`setSoundEnabled(bool)`, `STORAGE_KEY`. |
| `src/frontend/hooks/useAudibleAlert.ts` | Existing finding chime — replaces inline `playChime` call + inline `isSoundEnabled() && !isDndEnabled()` gate with a single call to `maybePlayChime()`. **No back-compat re-exports** — round-2 critics (design-minimalist + boundary-critic) confirmed that the only consumers are `SettingsDialog.tsx` and `StatusBar.tsx`, both of which can be updated in the same PR for a single-operator dashboard with no semver discipline. |
| `src/frontend/hooks/useTaskCompletionChime.ts` | **New.** Watches the focused agent's `taskStatus`. On non-terminal → terminal transition observed *while focused*, calls `maybePlayChime()`. ~50 lines. |
| `src/frontend/hooks/useTaskCompletionChime.test.ts` | **New.** ~150 lines. Mirrors `useAudibleAlert.test.ts` style with `vi.stubGlobal('AudioContext', ...)`. |
| `src/frontend/App.tsx` | Add `useTaskCompletionChime();` next to `useAudibleAlert();` with an inline comment documenting the focus asymmetry. |
| `src/frontend/components/SettingsDialog.tsx` | Update `isSoundEnabled`/`setSoundEnabled` import path from `../hooks/useAudibleAlert.js` to `../audio/sound.js`. One line. |
| `src/frontend/components/StatusBar.tsx` | Same import path update. One line. |

`src/frontend/audio/` is a new top-level frontend folder. The `hooks/` directory is reserved for files that use React hooks (boundary-critic finding); keeping `playChime` in `hooks/` would violate the directory's implied contract. This is the first purpose-named leaf folder under `src/frontend/`; existing top-level folders are role-named (`components/`, `hooks/`, `store/`). The deviation is justified because `audio` is a clear noun bucket for primitives that may grow (e.g., distinct chime variants per Open Question 1) — splitting it into `audio/sound.ts`, `audio/chime-finding.ts`, `audio/chime-completion.ts` later is natural; rolling those into `lib/` or stuffing them into `hooks/` would not be.

**Pre-existing `audio/ → hooks/` import for `isDndEnabled`:** `audio/sound.ts` imports `isDndEnabled` from `hooks/useDnd.ts`. Round-2 boundary-critic confirmed this follows existing codebase precedent (`store/slices/triage-navigation-slice.ts:3` already imports `isDndEnabled` from `hooks/useDnd.ts`), where `useDnd.ts` exports both the React hook and the pure stateful function side-by-side. Splitting `useDnd.ts` into `dnd-state.ts` (pure) + `useDnd.ts` (hook wrapper) is a reasonable cleanup but is out of scope here — fixing it now would balloon the PR.

### 2. Hook implementation

```ts
import { useEffect, useRef } from 'react';
import type { TaskStatus } from '../../core/types.js';
import { isTerminalStatus } from '../../shared/contracts/task-status.js';
import { useKookrStore } from '../store/useStore.js';
import { maybePlayChime } from '../audio/sound.js';

interface FocusedStatus {
  agentId: string;
  status: TaskStatus | undefined;
}

export function useTaskCompletionChime(): void {
  const selectedAgentId = useKookrStore((s) => s.selectedAgentId);
  const agents = useKookrStore((s) => s.agents);

  // Tracks the focused agent's last-observed status. Reset whenever focus
  // changes, so a transition that happens while the agent is *not* focused
  // is not retroactively chimed when the user focuses back. This is the
  // "while focused" semantics required by the spec — round-1 failure-mode
  // finding.
  //
  // StrictMode dev-mode behavior: the React 18 docs do not guarantee that
  // useRef persists across the StrictMode mount→cleanup→mount cycle (the
  // observable behavior depends on whether React reuses the hook instance,
  // which is implementation-defined and may change with the Activity API).
  // The design is robust under either interpretation: if the ref persists,
  // the second mount sees `prev === next` and short-circuits; if the ref
  // resets to null, the focus-change branch below treats the remount as a
  // fresh focus and does not chime. (This deliberately diverges from
  // useAudibleAlert.ts:145-152's module-scoped state; round-2 failure-mode
  // finding confirmed the existing module-scope is over-defensive given
  // either StrictMode interpretation.)
  const focusRef = useRef<FocusedStatus | null>(null);

  useEffect(() => {
    if (!selectedAgentId) {
      focusRef.current = null;
      return;
    }
    const agent = agents.find((a) => a.agentId === selectedAgentId);
    if (!agent) {
      focusRef.current = null;
      return;
    }

    const next = agent.taskStatus;

    // Focus changed (or first observation): start tracking, never chime.
    if (focusRef.current?.agentId !== selectedAgentId) {
      focusRef.current = { agentId: selectedAgentId, status: next };
      return;
    }

    const prev = focusRef.current.status;
    // Write the ref BEFORE the chime decision: load-bearing. If maybePlayChime
    // ever throws synchronously, the ref already advanced to next, so the
    // following effect run sees no spurious transition (round-2 failure-mode
    // finding on order-of-writes).
    focusRef.current.status = next;

    // No transition.
    if (prev === next) return;
    // Transition into terminal from a non-terminal state.
    if (next === undefined) return;
    if (prev !== undefined && isTerminalStatus(prev)) return;
    if (!isTerminalStatus(next)) return;

    maybePlayChime();
  }, [selectedAgentId, agents]);
}
```

The scalar `useRef` with focus-change reset is materially simpler than v1's `Map` (round-1 design-minimalist + failure-mode finding) AND directly enforces the "while focused" requirement.

The `[selectedAgentId, agents]` dependency means the effect re-runs on every WS update of any agent (because `agents` is a fresh array reference each delta). For the focused agent that produces a redundant ref read+write but no chime; for non-focused-agent updates the focus check short-circuits early. Round-2 failure-mode flagged this as a potential perf concern at very high agent counts — at the project's expected scale (typically <50 agents) it is negligible. **Do NOT memoize on `selectedAgent.taskStatus`** — must observe every commit so a rapid sequence of transitions through a render boundary is not collapsed.

### 3. `audio/sound.ts` sketch

```ts
import { isDndEnabled } from '../hooks/useDnd.js';

const STORAGE_KEY = 'kookr-sound-enabled';

export function isSoundEnabled(): boolean {
  return localStorage.getItem(STORAGE_KEY) !== 'false';
}

export function setSoundEnabled(enabled: boolean): void {
  localStorage.setItem(STORAGE_KEY, String(enabled));
}

let warnedRejection = false;

/** Raw two-tone chime via Web Audio. Module-private — production callers
 * use maybePlayChime so mute/DND gates are applied uniformly. Tests reach
 * the audio path via maybePlayChime() with cleared mute/DND preconditions
 * (round-2 boundary-critic — exporting playChime would widen the public
 * surface for a test-only reason and create a gate-bypass footgun). */
function playChime(): void {
  try {
    const ctx = new AudioContext();
    // ... existing oscillator setup, byte-identical to useAudibleAlert.ts ...
  } catch (err) {
    if (!warnedRejection) {
      warnedRejection = true;
      console.warn('[kookr] AudioContext rejected; chime suppressed', err);
    }
  }
}

/** Gate-aware wrapper. The single public production entry point. Returns
 * early on mute or DND. */
export function maybePlayChime(): void {
  if (!isSoundEnabled() || isDndEnabled()) return;
  playChime();
}
```

The gate ownership lives in one place. Both `useAudibleAlert` and `useTaskCompletionChime` collapse to a single `maybePlayChime()` call instead of duplicating `if (isSoundEnabled() && !isDndEnabled()) playChime()` inline (round-1 boundary-critic finding). `playChime` stays module-private — exporting it for tests would widen the surface and create a gate-bypass risk for a future caller (round-2 boundary-critic).

### 4. Focus-asymmetry comment at App.tsx mount site

```tsx
useNotifications();
// Audible-alert hooks. Findings are unfocused (attention-routing — anomaly
// chimes regardless of which task is focused, because that's when the user
// most needs to switch focus). Completion is focus-gated (only the watched
// task chimes — non-focused completions are surfaced visually in the
// completed list). See rfc-task-chime-browser.md §6.
useAudibleAlert();
useTaskCompletionChime();
```

### 5. Test plan

**Pre-flight (must land before extraction):**
- Add to `useAudibleAlert.test.ts`: a smoke test that stubs `AudioContext` via `vi.stubGlobal('AudioContext', vi.fn())` and asserts the constructor is invoked when the hook fires for an active critical finding.
- **Critical (round-2 delivery-pragmatist):** the stub MUST target the right module after extraction. After Step 2, `useAudibleAlert.ts` no longer calls `new AudioContext()` directly — it calls `maybePlayChime()` from `audio/sound.ts`. `vi.stubGlobal('AudioContext', ...)` works because both modules read `AudioContext` from the global scope, so the stub catches both. **Verify** by running the test before AND after the extraction; if the call count drops to zero post-extraction, the stub is missing the new module path. Add a parallel test `audio/sound.test.ts` that calls `maybePlayChime()` directly with `localStorage` mute=false and DND=false, asserting the constructor is invoked — this is the canonical regression guard for the audio module post-extraction.

**`useTaskCompletionChime.test.ts` cases:**
- Hydration: focused agent already terminal at first observation → no chime.
- Transition while focused: agent goes `inProgress → completed` → chime fires once.
- Re-render with same status (e.g., delta updates an unrelated field) → no chime.
- Transition on **non-focused** agent → no chime (effect short-circuits on selectedAgentId).
- Mute toggle off → no chime even on transition (gate inside `maybePlayChime`).
- DND on → no chime.
- Stale-completion guard: focus A (inProgress) → focus B → A completes → focus back to A → **no chime** (focus-change reset cleared the prev status). **This case subsumes the "rapid focus-switch during transition" and "switch to never-before-seen terminal agent" v2 cases — they all assert the same property: focus changes invalidate prev status, so transitions not observed while focused never chime** (round-2 design-minimalist merge).
- Reopen → re-complete cycle (round-2 failure-mode finding): focus A (inProgress) → A completes (chime 1) → user reopens A → A goes inProgress → A completes again → **chime 2 fires** (legitimate new completion, not double-chime; the `prev` state cycled through non-terminal so the terminal-state guard does not fire).
- Self-completion: user-initiated `completeTask` produces a `completed` status delta → chime fires (current spec behavior; suppression is a future enhancement, see §Future enhancements).
- StrictMode: explicit `<StrictMode>` wrapper around the hook → exactly one chime on a single transition (covers both ref-persists and ref-resets interpretations).

**Existing tests:** `useAudibleAlert.test.ts` must still pass after `playChime` extraction (smoke test above guards this).

### 6. Focus-asymmetry rationale (preserved as code comment)

The existing finding chime is *not* focus-gated. Findings represent attention-routing — a critical anomaly on a non-focused agent is precisely when the user needs to switch focus, so the chime must reach them regardless of which task they're watching. Completion is the inverse: for non-focused tasks, the dashboard already surfaces the transition in the `completed` list. Audio for non-focused completions adds noise without information; audio for focused completions confirms what the user is already watching.

This asymmetry is not arbitrary, but it is load-bearing — if Open Question 4 ("chime for long-running background tasks regardless of focus") is later answered "yes," that decision *replaces* the asymmetry rather than extending it.

## Edge cases

- **Tab in background.** Web Audio plays through hidden tabs (same as existing finding chime). For "I walked away" use cases, see Open Question 3.
- **Browser autoplay rejection.** First chime on a fresh tab with no user interaction throws inside `AudioContext` constructor; `playChime` swallows the error and emits a one-time `console.warn`.
- **Stale-completion on focus return.** Resolved by focus-change reset — round-1 failure-mode F1.
- **WS reconnect after disconnect-during-transition.** If disconnect happens while focused agent is `inProgress` and reconnect arrives with `completed`, the chime fires. This may be a stale chime if the disconnect was long (e.g., laptop sleep). Acceptable v1 — the user is being told "this finished while you were away," which matches stated intent. If it produces too many surprise chimes in practice, a clock-skew check (suppress if `>5min` between disconnect and reconnect) can be added later.
- **Multiple tabs same focus.** Both chime independently. Acceptable per Non-Goals.
- **Agent removed mid-transition.** Early `return` on `!agent` prevents chime. Correct.
- **`selectAgent(null)` during transition.** Focus-change reset clears the ref; no chime.
- **`taskStatus === undefined`** (agents never associated with a task): the `next === undefined` guard prevents `isTerminalStatus(undefined)` issues.
- **`terminated → completed`** (post-ack flow): `prev` is terminal, `next` is terminal — guard `isTerminalStatus(prev)` returns false from chime path. No double-chime.
- **StrictMode (dev).** React 18's StrictMode mounts a component, runs effect setup + cleanup, then mounts again. The behavior of `useRef` across this cycle is **not contractually specified** — implementation-defined, may shift with the Activity API. The hook is robust under either interpretation: if the ref persists, the second effect run sees `prev === next` (or, after focus-change, the focus-change branch already primed the ref) → no chime. If the ref resets to null, the focus-change branch on lines `if (focusRef.current?.agentId !== selectedAgentId)` treats the remount as a fresh focus → no chime. The explicit StrictMode test case is the canonical guarantee. (Round-2 failure-mode finding: v2 misstated the React 18 ref-persistence contract as an absolute claim; the substance — both interpretations are safe — is correct.)

## Alternatives considered

### A. Foreground-marker file consumed by a shell hook

Kookr writes the focused taskId to `~/.claude/.foreground-task`; the shell hook gates on equality with `KOOKR_TASK_ID`. **Rejected:** durable cross-process state for a UI concern; the frontend already has perfect knowledge of focus.

### B. Use the Claude Code `Notification` hook

`Notification` fires when Claude needs attention (permission prompt, 60s idle). **Rejected:** wrong semantics; fires for permission requests, not completion.

### C. Use `SessionEnd` instead of `Stop`

**Rejected:** SessionEnd fires when the Claude Code process exits. For headless background tasks that's *more* often than `Stop`, not less.

### D. Shell-hook debounce wrapper

Suppress plays within N seconds of the previous play. **Rejected:** rate-limits but does not filter background tasks.

### E. Extend `useAudibleAlert` with a second predicate

Add a `taskStatus`-transition branch into the existing dedup loop. **Rejected:** the two triggers have different semantics — finding chime is *not* focus-gated, completion chime *is*. Cramming them into one hook means complicating the dedup state with a `Map` of finding-keys-or-status-transitions and either fanning the focus gate over both (regression on findings) or branching the gate per-trigger (uglier than two hooks).

### F. Do nothing — accept that the dashboard's visual state is sufficient

Remove the global Stop hook and add no replacement. The user sees green badges in the completed list. **Rejected** by the user's stated intent ("i want the sound to play only when main agent finished its task"). Recorded for completeness — round-1 socratic-challenger Q1.

### G. Inverted focus gate — chime for non-focused tasks only

If the user is already watching, their eyes have the badge; the chime is most valuable for tasks the user is *not* watching. **Considered (round-1 socratic Q2 + ambition-amplifier F2)** but in tension with the "storm" problem the RFC is solving: chiming for all background completions reproduces the storm at lower frequency. The duration-threshold variant is captured as Open Question 4 instead of replacing the focus gate.

## Migration / rollout

Purely additive frontend change. No flag. 4-PR sequence:

1. **PR 1 — Pre-extraction smoke test.** Add `vi.stubGlobal('AudioContext')` smoke assertion to `useAudibleAlert.test.ts`. Pure additive test, no behavior change.
2. **PR 2 — Audio module extraction.** Create `src/frontend/audio/sound.ts` (with `playChime`, `maybePlayChime`, `isSoundEnabled`/`setSoundEnabled`). Update `useAudibleAlert.ts` to call `maybePlayChime()`. Update `SettingsDialog.tsx` and `StatusBar.tsx` import paths in the same PR. Add `audio/sound.test.ts` with the canonical post-extraction smoke assertion. Existing finding chime must remain audibly identical.
3. **PR 3 — Completion hook.** Add `src/frontend/hooks/useTaskCompletionChime.ts` + tests, wire into `App.tsx` with the focus-asymmetry comment.
4. **Soak — user, not a PR.** Use the new chime for several working sessions covering all three terminal transitions:
   - **Step 4 success checklist (round-2 delivery-pragmatist):** before removing the shell hook, the user should have personally observed:
     - Completion chime fired on at least one **autonomous `completed`** transition (agent finished cleanly).
     - Completion chime fired on at least one **`cancelled`** transition (Alt+Delete or equivalent).
     - Completion chime fired on at least one **`terminated`** transition (sessions died — may require waiting for natural occurrence; if not seen in soak, document the gap and proceed).
     - Switching focus away from an in-progress agent and back after it completed off-screen does **NOT** chime.
     - At least one full WS reconnect cycle (laptop sleep / wifi flap) without a surprise stale chime that feels wrong.
5. **Manual edit — user.** Comment out (don't delete) the `Stop` block in `~/.claude/settings.json:67-77`. Re-enabling is then a 5-second uncomment if the new chime misbehaves later (round-2 delivery-pragmatist suggestion). Delete the commented block after a further week if no regression.

**During the soak (PR 3 → step 4 → step 5):** both chimes fire (browser + shell). Intentional dual-fire verifies the new path before removing the old. If the browser chime misbehaves during soak, the primary rollback is a **one-line revert of the `useTaskCompletionChime();` call in `App.tsx`** — clean, surgical, leaves the audio module and finding chime intact. `localStorage.setItem('kookr-sound-enabled', 'false')` is the emergency mute but silences the finding chime as collateral; prefer the code revert when the issue is specifically with the completion chime.

## Future enhancements (out of v1 scope)

- **Suppress chime on user-initiated completion (Alt+End / Alt+Delete).** Current behavior: chimes ~100ms after the user confirms the dialog. If this proves annoying in practice, the cheapest implementation is a client-side `pendingSelfCompletions: Set<taskId>` populated when `send({type: 'completeTask'})` is called and cleared on the corresponding terminal `update` arrival or after a 2-second timeout. The chime hook checks the set before firing. **Failure mode** (round-2 failure-mode): server slowness > 2s causes the suppression to fail open and a chime to fire ~2s after the click — acceptable degradation. The protocol-level alternative (add `clientRequestId` to `completeTask` schema and `cause` to update messages) is more reliable but expensive; the WS contract today carries no correlation token between `completeTask` send and the resulting `update` (round-2 failure-mode confirmed).
- **Distinct sounds per terminal status** (Open Question 1).
- **OS desktop notification when focused task completes and tab is hidden** (Open Question 2). Symmetric extension of `useNotifications.ts`.
- **Background long-running task chime** (Open Question 3). Duration-threshold variant.
- **Telemetry event `task_chime_played`** for diagnosability — currently no signal beyond `console.warn` on autoplay rejection. Not blocking; useful for verifying the system works in real sessions.
