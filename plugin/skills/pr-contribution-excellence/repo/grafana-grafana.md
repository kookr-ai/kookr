# grafana/grafana — Repo-Specific PR Patterns

Distilled from 15 PRs analyzed on 2026-03-30. Mix of community and internal PRs, merged and rejected.

## PR Title Format

`<FeatureArea>: Describe your change` — used for auto-generated changelog. Area names are UpperCamelCase or match area labels (e.g., `Alerting:`, `Dashboards:`, `CI:`, `Tempo:`, `Search:`). Recent community PRs also use `fix(scope):` format successfully.

## Squash Merge Policy

Grafana squash-merges all PRs. Commit count is completely irrelevant (50 commits merged fine). Focus entirely on:
- PR title quality (it becomes the commit message)
- PR description quality
- Final diff cleanliness

## PR Template Usage

- **Required for substantive changes**: Fill out What/Why/Who/Issue/Special notes
- **OK to skip for trivial fixes**: 1-line Makefile fixes merged with one-sentence descriptions
- **Mark N/A explicitly**: Shows you read the template (`N/A` on irrelevant checklist items)
- **Never leave placeholder text**: "[Add a brief description...]" signals you don't care — these PRs get closed or superseded
- **Internal contributors**: May use a simpler `## Summary` section instead of full template

## Review Pipeline

1. **GitHub Copilot** reviews automatically — generates 3-6 code comments on most PRs. Finds real issues (missing tests, type mismatches, namespace inconsistencies). Take seriously.
2. **CODEOWNERS auto-assignment** — don't manually tag reviewers. The 84KB CODEOWNERS file handles routing based on which files you touch.
3. **Human reviewers** dig deeper: semantic correctness, edge cases, architectural patterns, feature toggle discipline.
4. **Security scanners** (zizmor) flag issues in CI workflow files — may flag pre-existing issues in files you touch.
5. **grafana-delivery-bot** posts build links automatically.

## Stale Bot Rules

- **30 days inactive** → marked as stale
- **+14 days** → auto-closed
- **Survival**: Respond with anything ("This is not stale", "Nope this is still needed") to reset timer
- **Community PRs can survive 6 months** if you keep responding (evidence: #111735)
- **Being auto-closed is NOT rejection** — reopen and continue

## Scope Discipline

Grafana reviewers explicitly enforce scope:
- "This and the next two changes is the actual fix. Why do we need the rest of the changes?" (#120723)
- Extra changes will be asked to be removed before tests are requested
- Review flow is predictable: **scope reduction → test request → rebase request → approval**

## Test Expectations

- Tests required for all code changes — reviewers will ask if missing
- Pure refactors (component extraction) may skip tests
- Docs-only changes skip tests
- Copilot specifically flags missing test coverage for new code paths
- Test coverage CI runs per-codeowner with percentage tracking

## Visual Evidence

- **UI changes**: Before/after screenshots in side-by-side markdown tables
- **Bug fixes**: Screenshot of bug + screenshot of fix
- **CI/tooling**: Quantitative before/after metrics (variance, pass rates)
- **Features**: Video recordings demonstrating the feature
- **QA verification**: Screenshots from manual QA testing are valued

## AI-Generated PRs

Grafana accepts AI-generated contributions:
- "🤖 Generated with Claude Code" — merged (#120994)
- "This was generated by Cursor" — merged (#114047)
- Honest disclosure builds trust. No evidence of rejection due to AI generation.

## Feature Toggle Discipline

- Pre-GA features MUST be behind feature toggles
- Reviewers check behavior with toggle BOTH enabled AND disabled
- Serialization should always work (load saved data) regardless of toggle state
- Generated feature toggle files (Go, CSV, TypeScript) change frequently — expect noise in diffs

## Duplicate Prevention

ALWAYS search existing PRs fixing the same issue before submitting:
- Duplicates get closed politely but without ceremony
- Even excellent PR descriptions can't save a duplicate (#121041)
- Check both open PRs and recently merged PRs

## Community PR Survival Guide

1. **Pick the right area**: Frontend TypeScript PRs get faster review than niche backend Go areas
2. **Smallest possible change**: 1 file, 1 commit → merged in 26 minutes (#121334)
3. **Proactively include tests**: Don't wait for reviewer to ask
4. **Respond same-day to feedback**: Keeps momentum
5. **Open separate PRs for tangential fixes**: Shows scope awareness
6. **If no review after 2 weeks**: Escalate via community channels, not just GitHub pings
7. **Persist through stale bot**: It's a test of patience, not rejection

## Labels

Community PRs may not get auto-labeled. Key labels:
- `area/*` — triggers CODEOWNERS review assignment
- `no-changelog` — for non-user-facing changes
- `no-backport` — for changes that shouldn't be backported
- `add to changelog` — PR title used for changelog entry
- `pr/external` — applied to external contributor PRs

## Approval ≠ Merge: Follow Up After 3-5 Days

An approved PR is not necessarily merged. A reviewer may approve but forget to click merge. If your PR is approved but not merged within 3-5 days, ping the reviewer or the PR thread. Don't wait for the stale bot (30 days) — by then another PR may have fixed the same issue.

(Evidence: #119180 — approved day 1, sat for 31 days, then closed because another PR fixed the same typo first)

## Self-Review Comments Preempt Reviewer Questions

Leave inline comments on your own PR explaining non-obvious decisions before requesting review. Reference why you renamed files, chose a particular approach, or made architectural tradeoffs. This collapses reviewer questions into acknowledgments.

(Evidence: #120746 — self-review comments on renaming `sql` to `legacy-sql` and partition creation rationale prevented questions; #122016 — What/Why template sections preempted questions about nil-channel idiom)

## Vague PR Titles Invite Pushback

Titles like "improvements" or "updates" are a smell that signals unclear scope. Reviewers probe harder. Use specific verbs: "Fix race in batchRunner", "Remove dashboardAdHocAndGroupByWrapper", "Replace hardcoded error color with theme token." The PR title becomes the commit message under squash merge — it needs to be descriptive.

(Evidence: #120909 — "Bundled plugins improvements" combined two features, got architectural pushback and was closed)

## Feature Toggle Retirement Pattern

Removing a feature flag + all gated code paths + related tests in one PR is a common, low-risk cleanup contribution type. Always use `no-changelog` since it's invisible to users. Bundling a related dependency bump (e.g., `@grafana/scenes`) is acceptable if causally linked.

(Evidence: #122031 — toggle removal + dep bump + test deletion, merged in ~7 hours with single approval)

## Multi-Layer Deprecation Pattern

Deprecating API endpoints requires three simultaneous changes: HTTP response headers (`Warning`, `X-API-Deprecation-Date`, `X-API-Replacement`), OpenAPI `deprecated: true`, and markdown doc notices. Reviewers check for completeness across all layers.

(Evidence: #121995 — reviewer caught incomplete doc coverage and missing replacement API links)

## Codex Bot as Self-Review Tool

Authors can trigger `@codex review` as a pre-review self-check. The bot raises legitimate architectural concerns that the author can then address or rebut before human review. This demonstrates thoroughness and catches issues humans would flag.

(Evidence: #121814 — author triggered Codex bot 3 times; bot raised RV validation concern; human reviewer then focused on deeper debuggability issues)

## Debuggability Over DRY

Grafana reviewers prioritize observability and log specificity over code deduplication. A `conflictError()` helper that hides call-site context in logs will be flagged. Keep error construction at the call site so logs show exactly where the error originated.

(Evidence: #121814 — reviewer flagged that helper function hides call-site context; pattern consistent with observability-first culture)

## [no-op] Tag for Refactors

Starting a refactor PR description with `[no-op this is purely moving definitions around]` immediately sets risk expectations. Reviewers skip behavioral analysis and focus on mechanical correctness. Use for import swaps, constant relocations, and code-move refactors.

(Evidence: #122041 — 60-file refactor merged in ~1.5 hours with single approval after [no-op] tag)

## AI Co-Authored-By Trailer Accepted

Grafana accepts AI co-authorship disclosure via `Co-Authored-By: Claude Sonnet 4.6 <noreply@anthropic.com>` trailer. Reviewers approve without commenting on it. Honest disclosure is the right approach.

(Evidence: #122016 — both commits had Claude trailer, reviewer approved without mention; consistent with #120994 and #114047 AI disclosure patterns)

## Golden File Updates as Test Evidence

When the repo uses snapshot/golden-file testing, updating golden checksums IS the test evidence. It proves the entire test suite ran against the new behavior. Reviewers understand the +/- inflation from checksum changes.

(Evidence: #122052 — 279 lines of checksum changes accompanied a 60-line logic fix; merged in 37 minutes)

## Net-Negative Line Count Earns Trust

Bug fixes that reduce code by removing duplicated control flow get fast approvals. A PR that adds 12 lines and removes 31 signals the codebase is getting simpler. Combine with idiomatic language solutions (Go nil-channel-in-select, pattern matching) for maximum reviewer trust.

(Evidence: #122016 — net -19 lines, idiomatic Go fix, merged in 3.5 hours)

## Test Coverage as Core Deliverable

PRs where test lines significantly exceed production code lines get fast reviews. A +247 test / +60 production line ratio signals quality. Tests are treated as first-class deliverables, not afterthoughts.

(Evidence: #121814 — 4:1 test-to-production ratio, merged after 1 inline comment; #121572 — 14:1 ratio, zero comments)

## Commit SHA References in Review Responses

When addressing review feedback, reference the specific commit SHA: "Does this capture what you had in mind: <sha>?" This makes re-review efficient by pointing the reviewer directly to the fix.

(Evidence: #120746 — author responded to every comment with specific commit SHA links)

## Manual Reproduction Steps in Descriptions

Include concrete API URLs or commands for manual testing in the PR description, even for backend plumbing. This helps reviewers verify quickly without reading the diff.

(Evidence: #122052 — included `/apis/dashboard.grafana.app/v0alpha1/namespaces/default/dashboards/adbbsdl` as test URL)

# Additional Patterns (from Stream 2 analysis)


## Coverage Checks Are Advisory, Not Blocking

The `grafana-pr-automation[bot]` posts test coverage reports per-CODEOWNER team. Failing coverage (lines/branches decreasing) does **not** block merge. PRs with failing coverage checks merged via auto-merge without the `no-check-frontend-test-coverage` bypass label (#121370). The label exists for meta-CI fixes (#121382) but isn't needed to override. Even a 16:1 test-to-fix ratio can show slight coverage decrease (#121275: -0.02% line, -0.29% branch) — accepted without comment.

Implication for external contributors: Don't panic about failing coverage checks. They're informational. But still aim for net-positive coverage — reviewers notice even if bots don't block.

## Single Approval Is Sufficient

Every PR in our sample merged with exactly 1-2 approvals, despite 2-5 additional requested reviewers who never responded. There's no multi-reviewer gate for any PR type: features (#121110), bug fixes (#121374, #121452, #121369), refactoring (#121355), CI fixes (#121382), or migrations (#121028). The pattern is: one teammate approval → author self-merges.

Exception: streaming/infrastructure PRs (#118631) may require dual approval — one for code correctness, one for manual integration testing.

## Feature Toggle Prerequisites in Test Plans

Grafana has dozens of feature toggles. For features behind toggles, the test plan MUST list which toggles to enable. Example from #121110: "Enable `alertingMultiplePolicies`, `alertingListViewV2`, `alertingFilterV2`." New behavior must be gated behind a feature toggle (#118631: `forwardTeamHeadersTempo`), and reviewers enforce toggle naming and encapsulation hygiene.

## Review Dynamics: Engagement Over Agreement

Successful review interactions across 25 PRs:
- **Acknowledge all nits** with reactions, even if not implementing (#121110)
- **Find middle ground** on naming suggestions rather than blindly accepting or defending (#121374)
- **Add tests when requested** without pushback (#121370)
- **Adopt architectural suggestions** and put them in a dedicated "Code review changes" commit (#121110)
- **Implement reviewer's preferred approach** even if yours is also correct — it's the fastest path to merge (#120994: ashharrison90 preferred consolidation into `outsidePress` function)
- **Respond with commit reference**: "Does this capture what you had in mind: <sha>?" (#120994) — makes verification easy
- **Batch-address all comments in one session** — concise responses like "good call out, done" are appreciated (#118631)

## Mechanical Migrations: High File Count Is Fine

72-file migration with near-zero net change (+128/-127) merged with single approval (#121028). Key: balanced additions/deletions signal systematic find-and-replace, not a sprawling feature. Single atomic commit is preferred for this type of change.

## Storybook as Testing Infrastructure

Interactive Storybook stories (dismiss buttons, `useArgs` patterns) count as visual testing at Grafana (#121355). This is valued even without assertion-based tests. For UI component refactoring, updating stories may be sufficient test coverage.

## Internal Export Pattern

New UI components go to `@grafana/ui`'s `src/internal/index.ts`, not the public API barrel (#121355). The `ModalBase` component was exported internally only. External contributors should follow this pattern for new components unless explicitly instructed otherwise.

## Codex Bot as First-Pass Reviewer

Some teams use `chatgpt-codex-connector[bot]` via `@codex review` before requesting human review (#121266). Responding constructively to bot findings — even to disagree — demonstrates engagement. After pushing fixes, re-trigger with `@codex review`.

## AI Assistance Disclosure in Commits

- Claude co-authorship is normalized: `Co-Authored-By: Claude Sonnet 4.6 <noreply@anthropic.com>` draws zero reviewer friction (#120994, #120909, #121445).
- Commit messages referencing "slop" (AI-generated code) are red flags (#121448: "Revert slop", "Remove slop comment"). Squash these away before opening a PR.

## Ephemeral Deployment Is Best-Effort

`/deploy-to-hg` triggers ephemeral instance deployment. Failures don't block merge (#121028 — two deployment failures, still merged). The feature is useful for UI validation but not a hard requirement.

## Auto-Merge for High-Confidence Changes

Internal contributors enable auto-merge (squash) on PRs when confident CI will pass (#121435, #121370). This is normal workflow, not cutting corners. The PR merges automatically once the single required approval lands and CI passes.

## Bug Bash PRs

"Bug bash fixes" is a recognized PR type (#121370, #121275) — multiple small related fixes bundled into one PR. Acceptable when all fixes are in the same feature area. Use one commit per logical fix (#121275: two bugs = two commits). Reviewers may still ask for specific test coverage for individual fixes.

## Self-Annotation Guides Reviewers

Authors who leave inline comments on their own PR marking "this is the key to the fix for X" (#121275) dramatically reduce review time. Reviewer approved within 35 minutes of self-annotations. Especially useful for multi-fix PRs or when the critical change is buried in a larger diff.

## Bugfix Description Gold Standard

The ideal bugfix PR body follows: **expected behavior → observed behavior → root cause → fix strategy → linked issue/escalation** (#121369). Short, precise, no fluff. Support escalation links add urgency and accelerate merge velocity for internal contributors.

## Post-Merge Label Audit Culture

Labels get audited retroactively — another team member may ask post-merge whether `breaking-change` should be added (#121222, deprecation context). For external contributors: get labels right upfront. When adding opt-out labels (`no-backport`, `no-changelog`, `no-check-mt-service-compatibility`), explain why in a PR comment.

## Study the SDK Before Proposing Solutions

First-review approach pivots are the biggest time sink (#118631: 18 days lost). The original implementation reconstructed something the framework already provided. Grafana reviewers are domain experts who will redirect your entire approach if the framework already solves the problem. Study the SDK, check existing middleware, and understand the data flow before writing code.

## External vs Internal Contributor Bar

| Dimension | Internal | External |
|-----------|----------|----------|
| PR template | Often skipped (#121438, #121429) | Must fill completely |
| Tests | Sometimes skipped for trivial fixes (#121369) | Always include tests |
| Description | Can be brief (#121222: 2 sentences) | Must explain what/why/impact |
| Self-merge | After single approval | Wait for maintainer to merge |
| Coverage bot | Advisory, never blocking | Likely held to higher standard |
| Commit history | Messy is fine (squash merge) | Clean commits show diligence |

## Squash Merge Is Universal

Grafana squash-merges all PRs. Messy commit histories (#121222: 4 commits, #118631: 30 commits) and clean ones (#121369: 1 commit) all produce identical clean merge commits. The PR title is the commit message — focus on getting that right using the `Area: Description` format.

## Feature Flag Governance Is High-Visibility

Feature flag status changes (e.g., experimental → publicPreview) attract unusually wide review — PR #121475 got 4 approvals including CTO torkelo for a 4-file, 28-line metadata change. This signals feature flags are governance items, not just code config. When correcting feature flag status, link to the public announcement that contradicts the current code — evidence-based descriptions are compelling.

Implication for external contributors: Feature flag changes are safe contributions with high visibility. But get the evidence right — link to the official release notes or what's-new page.

## Paired PRs for Cross-Layer Changes

Backend and frontend schema changes are split into paired PRs merged sequentially (#121236 backend + #121238 client). The naming convention creates implicit cross-references. Merge order: backend first, then client. The client PR may wait days post-approval until the backend PR merges.

Implication for external contributors: If your change spans backend and frontend, split it. Name them consistently so reviewers see the connection.

## Observability/Instrumentation PRs Get Minimal Scrutiny

Logging and metrics instrumentation PRs merge with silent approval and no tests (#121521: +50/-14, zero comments; #121550: +527/-3, zero comments). The Zanzana team reviewed two sequential instrumentation PRs from the same author with the same reviewer (mihai-turdean ↔ alexanderzobnin), demonstrating pair-review continuity for related work.

Implication for external contributors: Instrumentation PRs are low-friction contributions, but domain trust is key. Start with tests or docs to build trust before proposing instrumentation changes.

## Pattern Replication PRs: Show All Instances

When adding the same component to multiple locations (e.g., "Query with Assistant" button to MySQL and Postgres), include screenshots for every affected location (#121487: 4 screenshots covering both datasources). This visual completeness signals thoroughness and gets silent approval.

## Config Snippets in PR Description

For configuration-driven features, include a concrete config snippet in the PR description showing how to enable the feature (#121550: INI block for `[zanzana.client]`). This gives reviewers and future searchers immediate operational context.

## PR Ordering Dependencies Are Informal

When PRs must merge in order, authors state this in the description: "Should be rebased and merged after #121521" (#121550). There's no mechanical enforcement — it's trust-based. Authors are expected to manage the merge sequence themselves.

## Flag Known Limitations in PR Descriptions

Proactively documenting what your PR does NOT solve prevents reviewer confusion and demonstrates engineering maturity. Authors who include a NOTE section listing known limitations (e.g., "basic roles still have legacy access to the default route") get smoother reviews than those who present incomplete features as complete (#121034).

## Domain Experts Catch Fresh-Install vs Upgrade Path Issues

For DB migration PRs, general reviewers approve the SQL correctness, but domain experts catch environmental assumptions. The IAM expert on #121034 proved with a MySQL query that managed built-in roles don't exist on fresh installs — a gap two other approvers missed. Always ask: "does this work on a brand-new instance?" for any migration or seeding logic.

## "Implicitly Tested" Is Valid When Pointed at Specific Assertions

When asked why a migration doesn't have its own test, pointing to existing integration tests that assert the expected behavior is stronger than adding an isolated migration unit test. The key: name the specific assertion, don't just say "covered by integration tests" (#121034).

## Dependency Blockers Should Be Called Out Explicitly

When a PR is blocked on another PR, comment proactively: "Blocked by #121372 that renames actions" (#121034). This keeps reviewers informed and avoids wasted re-review effort. Silent waits waste everyone's time.

## Parameterized Tests (`it.each`) Are Welcome

Table-driven/parameterized tests using `it.each` are actively used and valued in Grafana's frontend codebase. Good pattern for testing the same behavior across multiple panel types or configurations (#121490).

## Reviewers Manually Test UI Features

Grafana reviewers record screen recordings and manually test UI features before approving — even for internal PRs (#121490). External contributors should expect this level of scrutiny and include instructions for manual testing.

## High Test-to-Code Ratio Gets Zero Review Comments

A test-to-code ratio of 14:1 (219 lines of table-driven tests for 16 lines of handler change) produced zero review comments and instant first-round approval (#121572). Similarly, 2.4:1 for a config fix got 24-minute approval (#121498). Over-testing is the fastest path through review.

## Grafana Commit Convention: `area: lowercase description`

Not Conventional Commits (`feat:`, `fix:`). The format is `area: description` in lowercase. Examples: "annotations: support query params in tags handler", "Alerting: Add access control for managed routes". The area prefix maps to team ownership.

## Design Tradeoff Documentation Preempts Reviewer Questions

Including an "Implementation notes" section listing alternatives considered and why they were rejected collapses review rounds to zero. #121501 documented 3 design tradeoffs and got two silent approvals within 5 hours. Front-load the "why not?" answers.

## Migration Screenshots for All Supported DBs

Showing actual DB migration results for MySQL, SQLite, AND Postgres builds concrete confidence (#121501). Abstract claims ("the migration is idempotent") don't carry the same weight as screenshots proving it ran successfully on all three.

## Docs Updates Included in Same PR

Grafana expects API docs and provisioning docs to be updated in the same PR as the backend change, not in a separate follow-up (#121501: type/docs label alongside area/backend). This is different from repos that prefer separate doc PRs.

## Stacked PR Series: Use "(1/N)" Naming Convention

Numbering PRs in a series ("Extract UI toggles hook (1/3)") sets reviewer expectations about scope and future work (#120136). The reviewer knows this is intentionally partial and approved faster. Long time-to-merge (20 days) isn't stalling — it's deliberate coordination of the merge sequence.

## Refactors That Improve Coverage Metrics Are Easy Wins

The grafana-pr-automation bot tracks per-CODEOWNER coverage. A refactor that improves coverage (+0.90% lines, +1.27% functions) is an easy path to approval because it shows the change is both safe (refactor) and beneficial (coverage up) (#120136).

## Performance PRs Need Causal Chains, Not Benchmarks

Performance PRs at Grafana get reviewed for the quality of the root-cause explanation, not for benchmark numbers. Describe what was slow, why (e.g., xorm reflection, slice reallocation), and how your fix addresses each cause. Domain-specific reviewers validate the reasoning (#119378).

## CI Experiment PRs ("Test Flights") Are Normal

Internal contributors open throwaway PRs to validate CI pipeline changes — opened, validated, closed without merge (#121499). The grafana-pr-automation coverage bot is the real "reviewer" for these. Not all closed-without-merge PRs represent rejection.

## Get UX/Product Alignment Before Coding Non-Trivial UI

Senior maintainers (torkelo and others) will challenge fundamental UX direction — not just implementation details. When a senior maintainer disagrees with the core approach, the result is full rework, not incremental fixes. PR #121474 was closed entirely because torkelo proposed a different UX pattern (keep card-based type selector for creation, add small type-change affordance in edit pane).

For external contributors: before coding any non-trivial UX change, socialize the design in an issue or RFC. Link to the design approval in the PR description. This is different from the SDK-study pattern — it's about UX direction, not implementation approach.

## Close Superseded PRs with Thread Context

When closing a PR in favor of a new one, reply in the review thread explaining what changed and why before closing. Don't silently close. This preserves context for anyone watching the thread and shows responsiveness to reviewer feedback. #121474 was closed without a thread reply after torkelo's feedback — a minor etiquette gap.

## Cross-Repo PRs (OSS + Enterprise) Use Minimal Descriptions

Internal PRs that are counterparts to enterprise-repo PRs use one-line descriptions linking to the private PR (#121513: "Counterpart to [enterprise PR link]"). This works because the real context lives in the enterprise PR. External contributors cannot replicate this pattern — you must write self-contained descriptions because you can't link to private repos.

## Dependency Version Bumps Bundled with Features

When a feature requires an upstream dependency bump (e.g., @grafana/scenes), the bump is folded into the same PR rather than split out (#121444). Even when the reviewer suggested sequencing them separately, the author resolved it with a final "bump version" commit in the same PR. This avoids the overhead of a separate PR for a one-line version change.

## Stale Bot as Paradoxical Attention Trigger

The 30-day stale bot paradoxically triggers attention — PRs are often merged shortly after being marked stale (#118432: merged 4 days after stale warning, #119198: merged 2 days after). For long-lived PRs, leave coordination comments explaining the delay to prevent stale marking. If already marked stale, use the stale notice as an opportunity to re-ping reviewers.

## Copilot Reviews Are Purely Advisory

GitHub Copilot automatically reviews PRs and leaves inline comments. These are universally treated as advisory — never blocking, often ignored entirely (#121444: 4 Copilot comments, none addressed before merge). Don't waste time responding to every Copilot comment unless it's genuinely useful. This is different from human review comments, which must be addressed.
